Truth boundary

Read-only evidence, not automated service action

The experience can resolve approved context and return bounded evidence. It does not write CRM, message anyone, control an appliance, prescribe a repair, or claim a root cause.

Current proof

Deferred

Operation contract

Five bounded read-only operation classes

Inputs are schema-constrained; unsupported identifiers, fields, history windows, and questions are rejected.

OperationBounded behavior
SearchFind approved appliances using constrained identifying fields.
Resolve caseMap an approved service case to one appliance or return unresolved/ambiguous.
SnapshotReturn profile-only or connected evidence according to user, appliance, and mode authorization.
HistoryReturn known fields for fixed, approved windows only.
ExplainOrganize observations, limited deterministic interpretation, unknowns, and one next validation question.

Authorization

Policy is checked before evidence access

A token alone is insufficient; the service also checks the calling application, delegated permission, user assignment, evidence role, appliance scope, and requested mode.

  1. The user signs in through an approved Microsoft host.
  2. The host or Enterprise Token Store obtains a delegated token for the protected service.
  3. The service validates issuer, tenant, token version, expiration, audience, client, and scope.
  4. The user is mapped to an evidence role and appliance scope.
  5. The operation and evidence mode are checked before source access.
  6. Only approved fields and history windows are returned.

Evidence semantics

Unknown is preserved, not averaged away

Profile mode stays useful without diagnostic exposure. Connected mode adds only approved evidence, source time, freshness, units, and missing values.

Observations

What an approved source reported, with units and source time.

Interpretation

Limited deterministic organization of those observations.

Unknowns

Absent, stale, ambiguous, unavailable, or out-of-contract evidence.

Failure behavior

Fail closed without hiding uncertainty

A failure never broadens access, silently picks an appliance, or converts missing evidence into a diagnosis.

Invalid identity or scopeReject before operation discovery or evidence access.
Ambiguous identifierReturn unresolved/ambiguous; never guess.
Profile-only accessOmit measurements, alerts, settings, status, and firmware.
Stale or missing evidenceShow age or unknown; do not infer healthy or failed.
Unsupported requestReturn bounded validation guidance.
Widget or source unavailableUse a safe fallback and preserve authorization plus last known source time.

Verification and limits

Demo-ready does not mean production-designed

The proof validates the cross-host read-only pattern. Customer source quality, scale, network, retention, service levels, support, and value remain unverified.

Bounded proof acceptance

  • Allowed users see only assigned cases and appliances.
  • Profile mode omits connected evidence by construction.
  • Connected mode returns only approved fields and freshness.
  • Invalid tokens, mappings, fields, and windows fail closed.
  • Both hosts preserve the same evidence meaning.
  • The proof can be reset and removed cleanly.

Customer decisions

  • Models, journeys, sources, fields, and freshness rules
  • Case/appliance relationship and ambiguity behavior
  • Network, region, persistence, retention, replay, and audit
  • Scale, recovery, support, incident response, and security operations
  • Credential strategy and rotation
  • Packaging, promotion, rollback, measurement, and rollout
